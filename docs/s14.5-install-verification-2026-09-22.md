# S14.5-T5 — on-device verification (2026-09-22)

Shell-driven install on the ROG Ally, from a freshly flashed live USB.

## Verified

| Step | Evidence |
|---|---|
| Shell drives the install, no second app | the shell stays on `SCREEN_INSTALLER` for the whole run |
| Progress visible in the shell | steps + percentage as they run (~6 s total), then the success card — confirmed on screen by the user |
| `PrepareInstall` | `PrepareInstall ok for /dev/nvme0n1`; a target holding `/` or `/data` is rejected |
| Payload device | `StartInstaller payload device: /dev/sda2` — the **stick's** payload, not the internal disk's `playos-a` |
| Worker starts, session intact | `install worker started (PID 345, target /dev/nvme0n1) - shell keeps the screen`; compositor, shell, overlay and SSH all stay up |
| All eight steps | worker log: steps 0–7 `ok`, `playos-install-worker: install complete` |
| Progress relayed | shell log: `install progress: step N (P%) <name>` … `install complete - showing the success card` |

## Still to verify

- **Standalone installer** — a `playos.mode=install` run, or `PLAYOS_INSTALL_TARGET`

## Bugs this run found (all fixed)

Four defects, each of which only showed up on hardware, and three of them the same
kind of mistake — the second front-end exposing something the first one assumed:

1. **Payload looked up by name.** `playos-a` exists on both media; init's label
   lookup found the internal disk's (a raw squashfs slot) and `mount` failed with
   `EINVAL`, so the worker never started. The shell already discovered the payload
   by *contents*, so it now passes that device through `StartInstaller`.
2. **Device path double-prefixed.** The shell sends `/dev/nvme0n1` and the step
   helpers add `/dev/` themselves, giving `fdisk_assign_device(/dev//dev/nvme0n1)`.
   The engine now normalises once at its boundary (a no-op for the standalone
   installer's bare names).
3. **Mountpoints assumed.** `efi.c` mounts at `/mnt/efi` without creating it, and
   only the standalone installer's `main()` did that — so step 6 died with
   `mount /dev/nvme0n1p1: No such file or directory`, which reads like a missing
   device but was a missing directory. The engine now creates its own mountpoints;
   `efi.c` creates its own like `format.c` already did.
4. **Leftover screen switch.** The hold branch still ended with
   `current_screen = SCREEN_SETTINGS` from S14-T10, when the install was a handoff
   to a separate app. T4 replaced the handoff but not that consequence, so every
   card was drawn on a screen nobody was looking at — the shell logged all eight
   steps and the success card while the user watched Settings, which still offered
   "Install PlayOS". A complete install looked like nothing had happened.
